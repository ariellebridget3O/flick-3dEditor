**Date**: 2026-11-14 · **Auditor**: task 2-a · **Mode**: read-only (no files modified)

## 0. Headline findings (must-fix first)

1. **P0 — `evalObjectItems` (Q) never seeds the TRS accumulators from the object's base TRS.** The original `L()` preloads shared temps `T/E/A/C` from the object record (`objects:…` @5696719+, raw:L201) *before* calling `Q`; the reconstruction creates `T=new Vector3()` (origin), `A=identity`, `S=(1,1,1)` (tracks.js:386). Verified by execution: a `rotate` item on a prop at (3,0,2) evaluates to `position=[0,0,0]`, identity-based rotation, `scale=[1,1,1]` → the mesh is teleported to the origin and loses base rotation/scale. Affects rotate/scale/revolve on **every** object kind (including persons whose path finished — the original keeps them at the path end via `ne()`-written `T`).
2. **P1 — `buildTangents` (mT) uses chord length, the original uses `Math.sqrt(chordLength)`.** Bundle @3926329: `const n=(l,c)=>Math.sqrt(xU(l,c))` with `xU=Math.hypot` (@3926101). `TRACK_SYSTEM.md §3.1` mis-transcribes this as `Math.hypot` and the reconstruction inherited the error. Middle-anchor tangents (and hence curve shape, arc length, derived duration) diverge whenever anchor spacing is uneven. (The pre-verified `out[0]=[0.67,0,0.33]` only exercises the *first* anchor, where `out=(next−cur)/3` and the sqrt cancels — it cannot discriminate.) Numeric example, anchors [0,0,0],[1,0,0],[1,0,4]: original `out₁=[0.444,0,0.444]`, arc 5.078, dur 3.627 s; reconstruction `out₁=[1.067,0,0.267]`, arc 5.247, dur 3.748 s.
3. **P1 — two rotation-direction sign flips vs the original**: `pan_sweep` in `camMovePose` (original `KCe` @3919105 rotates the look target by **+b**: `lookAt=[o+f·c+g·s, l+m, c−f·s+g·c]`; reconstruction rotates by −b) and `revolve` in `evalObjectItems` (original `x2r` @3922820: `x'=x·c+z·s, z'=−x·s+z·c`; reconstruction: `x'=x·c−z·s, z'=x·s+z·c`). Both verified by execution (pan_sweep ccw 90° from target (0,0,−5): original looks at (−5,0,0), reconstruction at (5,0,0)).
4. **P1 — camera resolver drops the original's no-subject fallback** (consumer, main.js:239): original `resolveAim(null)` returns the camera's **target object** position (`cameraTargetLine`), so subject-less `cam-move`/`cam-path` items orbit/dolly around the target marker. The reconstruction's `aim()` returns `null` → `evalCameraItem` treats the item as a no-op (`if (!target) {out.fovDeg=…; return;}`). The reconstruction's own auto-added default orbit cam-move (ui.js:328/558, no subjectId) therefore never animates.
5. **P1 — migration validators too lax** (`validPace`/`validHeightCurve` vs `X2r`/`Kzt` @4315100+): missing pace 0..1 element range, missing heightCurve `u[0]===0`/`u[last]===1` endpoints and `in/out` [2]-finite/`in[0]≤0≤out[0]` checks, `length≥2` relaxed to `≥1` — malformed fields the original drops are kept and later produce NaN/garbage eval.
6. **P1 — `v7to8` unwrap is not chained**: original `p6r` unwraps each key relative to the previous key's **unwrapped** value (`l` accumulator); the reconstruction re-wraps relative to the raw previous key. E.g. keys [0,4,8] rad → original [0,−2.283,−4.567] (continuous), reconstruction [0,−2.283,+1.717] (discontinuous). Also `v4to5` skips cameras without `shot` (the original processes *all* v4 cameras).
